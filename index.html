When an LLM spills out of VRAM, throughput drops 20–40× and nothing reports an error. The server returns 200 OK, the logs are clean, the fans are quiet. This toolkit measures the one number that explains it. 

$ python scripts/ollama-doctor.py --bench
[ ok ] server: responding at http://127.0.0.1:11434, version 0.40.1
[ ok ] context env: OLLAMA_CONTEXT_LENGTH=32768
[ ok ] launch path: ollama.exe running with `serve`
[warn] offload qwen3.6:latest: only 58% in VRAM (13.0 of 22.6 GB)
[fail] bench: qwen3.6:latest: 0.5 tok/s (32 tokens)

Real output from a 16 GB workstation. Same model, same card, had previously been measured at ~21 tok/s — the only difference was how much VRAM was free when it loaded.

Two numbers make every slow model explainable

Almost every "my hardware can't handle this" is a configuration fault, and it reduces to fit and context. Once you can see both, the fix is usually free.

OffloadWhat it means
99–100%Fully resident. If it's still slow, look at power limits, PCIe width, or thermals — not the model.
50–99%Partial offload. This is the 20× slowdown zone, and the most common single cause of a "broken" setup.
< 50%Effectively CPU inference. A bigger GPU helps, but fixing the fit is free and helps more.

Fixes in order of cost: reduce context length (the KV cache is often the hidden consumer), drop one quant tier, quantise the KV cache, or accept the offload and expect ~1 tok/s.

Why the numbers hold up

  • Weights come from the actual file size in the Hugging Face listing — not params × bits / 8, which ignores metadata, padding, and per-tensor quantisation differences.
  • KV cache is computed from the model's real config.json: layers × kv_heads × head_dim. No rule of thumb.
  • Throughput is measured on your machine, reported next to the offload percentage so the figure means something.
  • Verified: predicted 4.683 GB of weights for a 7B at Q4_K_M; the real file is 4.683 GB.

Questions

Will this make my model faster automatically?

No, and be suspicious of anything that claims to. It measures and reports. Most of the time the report itself is the fix — for example discovering your context length is set higher than your card can hold. It is read-only by design.

Does it work on AMD or Apple Silicon?

The Ollama checks work anywhere the API is reachable. The GPU row uses nvidia-smi and reports "not found" elsewhere, which is a normal result, not a failure. vram-fit.py is fully hardware-independent — it computes model requirements.

Is there a refund policy?

Yes. If it doesn't identify a real issue on your machine, say so and get your money back. It's a $19 diagnostic, not a subscription.

Why not just use a VRAM calculator website?

A calculator tells you what a model needs in theory. This reads what your model actually is, and what your machine is actually doing right now. The gap between those two is where most of the confusion lives.
